# Paramètres compte et messages — audit préparatoire

Lecture effectuée pendant la validation de l’import, sans modification de ces surfaces.

## Modèles de messages

Page, TemplateEditor, draft-state + dix tests adjacents, registre et API lus ; handlers/service/permissions serveur lus. Deux modèles réels : order_recap et delivery_reminder, chacun FR/EN/HE. GET SettingsView, PUT/DELETE SettingsEdit, restaurant explicite. PUT sauvegarde d’abord la source puis tente les traductions ; translation_error est un avertissement avec source confirmée. DELETE ne touche que la personnalisation clé/langue. Le service borne len(body) à 8 000 **octets UTF-8**, malgré son commentaire « characters ». Ne pas imposer silencieusement une limite de caractères différente. La traduction des autres langues doit encore être lue dans translate.go.

Le flux existant protège les saisies pendant PUT et dans d’autres onglets via dirtyRef et runSaveFlow ; ne pas le régresser. Un rechargement GET échoué ne transforme pas le succès d’écriture en échec. Défauts relevés : pas de verrou synchrone, chevauchement possible des mutations ; états non isolés au changement de restaurant ; GET initial sans reprise ; reset sans confirmation et sa réussite invisible si GET échoue ; source confirmée non appliquée au baseline local avant GET ; pas de garde beforeunload ; textarea sans nom accessible ; prévisualisation verticale peu exploitable sur desktop, messages longs pouvant déborder, état lecture seule abaissé à 70 % d’opacité. Édition pendant reset doit être maîtrisée, édition pendant PUT doit conserver les nouvelles frappes. Tokens/registry/buildOrderRecap/buildDeliveryReminder ne doivent pas changer leurs calculs ni le texte par défaut. Aucun vrai envoi dans les tests.

Piste : workspace keyed rid, chargement/reprise explicites, verrou mutation unique, baseline local confirmé et GET retry distinct, confirmation reset par clé/langue, conservation des autres brouillons. Réutiliser runSaveFlow et ses dix tests ; marquer la synchronisation en attente sans annoncer une sauvegarde échouée. Labels, aperçu parallèle, tokens clavier/caret, badges source/traduction et brouillons. État fictif de l’aperçu explicitement nommé.

## Sécurité / clés d’accès

Page entière et API 2490–2590 lues. Passkeys scoping utilisateur JWT, **pas restaurant**. Support vérifie authentificateur plateforme ; inscription begin/startRegistration/finish puis marque foody.passkey.device. Suppression dernière clé enlève ce hint local, jamais une permission de sécurité. Protocoles/auth API restent intacts. Défauts : GET échoué masqué comme liste vide ; support absent masque aussi la liste existante ; suppression sans confirmation, boutons sans nom de clé ; pas de verrou mutation commune ; nom modifiable en cours d’inscription ; noms tronqués et ligne ajout trop large mobile ; dates non localisées selon UI. Erreurs NotAllowedError/AbortError sont annulations normales, InvalidStateError est clé déjà enregistrée. Validation navigateur devra simuler WebAuthn/HTTP sans créer de vraie clé.

## Notifications — lecture préparatoire uniquement

Page et push.ts entièrement lus, routes serveur vérifiées. Préférences par utilisateur/restaurant, endpoints protégés par EnforceRestaurantAccess mais pas de SettingsEdit serveur ; UI actuelle réserve édition à settings.edit et autorise test abonné en lecture seule. Ne pas changer arbitrairement cette matrice. Abonnement PushManager local et enregistrement serveur sont deux phases. Current subscription attend serviceWorker.ready indéfiniment sans service worker ; refresh séquentiel masque aussi les erreurs prefs/devices. Préférences optimistes peuvent se clobber avec deux requêtes ; seuls les contrôles de la même clé sont désactivés. Suppression courante fait DELETE puis unsubscribe et masque les échecs ; unsubscribe du module masque déjà l’échec serveur et privilégie l’arrêt local. Préserver le protocole et documenter/rendre visibles ses limites plutôt que revendiquer une désinscription serveur prouvée. Le test Push ne doit pas réellement partir : mocks SW/Notification et routes API isolées. Switch translate-x n’est pas RTL, labels appareils tronqués, actions de suppression non spécifiques, chargement/vide/erreur manquants. Une réconciliation explicite après mutation et des verrous globaux seront nécessaires. Aucun changement ici pour l’instant.

translate.go lu : source sauvegardée, autres langues absentes/auto-traduites uniquement ; les langues personnalisées à la main restent protégées. Timeout 8 s par traduction, échecs partiels signalés ; tokens protégés/restaurés. Garder cette distinction dans les badges et reprises. Dix tests draft-state doivent être exécutés explicitement car le script npm ne découvre pas toujours les chemins avec [restaurantId].

## WhatsApp — audit page uniquement

Page complète lue. GET expéditeur et GET paramètres OTP séparés mais erreurs mélangées ; chargement settings échoué laisse « required » affiché comme si connu. Statuts ONLINE/OFFLINE/FAILED terminaux, polling 5 s sinon, sans invalidation des réponses ni verrou. Connexion Meta SDK via variables NEXT_PUBLIC_META_APP_ID, WA_CONFIG_ID, TWILIO_SOLUTION_ID et version Graph ; aucune valeur/env modifiée. postMessage actuel endsWith('facebook.com') accepte un hôte trompeur ; devra être borné aux origines HTTPS facebook.com / sous-domaines et à une inscription réellement lancée. IDs FINISH alimentent une revue avant confirmation numéro/nom puis connectWhatsApp. Déconnexion sans confirmation ni catch. Aucun texte traduit sauf lien modèles ; nombres/emails sans bidi, formulaire d’OTP affiche deux estimations de coût non issues d’un contrat API et un conseil anti-fraude non justifié. Ne pas inventer de tarifs : documenter l’écart et retirer les assertions non vérifiables de l’interface si aucune source projet ne les confirme. Il reste à lire API+serveur WhatsApp et OTP avant toute modification. Aucun connecteur ni message externe appelé.
