# Profils d’impression — audit préalable

Page, drawer, éditeur plein écran, affectations, options, composant JobSection et test adjacent lus intégralement. API profiles/printers/agents et contrats Go printing/profiles.go (CRUD, normalisation, catégories, affectations), handlers et routes parcourus ; dispatch confirme que category_custom suit SortOrder des catégories, pas l’ordre des IDs sélectionnés. Comparables : Appareils, Codes promotionnels, Parcours de commandes.

Contrat : nom unique insensible à la casse, trim et max120 octets UTF-8 (pas120 caractères). Types receipts/dine_in_tickets/online_tickets, au moins un ; tous champs remplacés, copies1–5. Catégories globales au restaurant, IDs validés même si type inactif. Auto-nouvelles catégories ajoute dynamiquement les catégories inconnues au snapshot lors de la lecture. Duplicate choisit le suffixe anglais (copy), ne copie pas les affectations et peut rejeter un nom trop long. Delete transactionnel supprime profil/affectations, préserve matériel et historique. GET après mutations peut échouer après persistance.

Affectations : remplacement intégral atomique. Chaque device_id doit être un agent connu du restaurant et printer_id une imprimante observée par cet agent ; nom effectif pris côté serveur. Liste agents exclut les oubliés ; printer_ids peut être null. Éditeur actuel construit les affectations par agents.flatMap et perd donc silencieusement les agents absents. Les imprimantes disparues doivent rester explicitement représentées jusqu’à retrait volontaire.

Permissions : lecture printers.view/manage, mutation printers.manage. API dédiée GET printing/spooler/categories existe pour ces permissions ; frontend utilisait getAllCategories qui requiert menu.view. Ne pas élargir les permissions du rôle pour contourner.

Autres défauts : DesktopOnly, table non adaptée mobile, options partagées dupliquées sous deux types, popover catégories flottant, contrôle switch physique RTL, lignes non clavier, chargement lié à t, absence de génération, verrous/validation ACK/récupération et gardes de brouillon. À conserver : tous paramètres, données historiques et associations, droits en lecture seule, création/duplication/suppression/recherche et aide. Aucun changement backend, aucune impression ni mutation réelle pour la preuve.

## Réalisation et vérification

Page responsive, cartes mobile/table desktop, recherche incluant affectations, détail exhaustif même en lecture seule ; option DesktopOnly retirée de la page/navigation. Éditeur à paramètres communs uniques, scopes par type et options cachées conservés, sélection globale limitée aux catégories disponibles, IDs inconnus explicitement conservés. API dédiée spooler/categories centralisée, pas de menu.view requis. UTF-8 max120 octets vérifié sans troncature, nom unique localement puis validation serveur.

Affectations complètes construites depuis le brouillon, y compris agents absents ; imprimante non observée visible et conservée jusqu’au choix explicite. Les options disponibles restent limitées à celles observées par l’agent. Un appareil manquant peut être retiré/restauré explicitement dans le brouillon. Backend peut rejeter une affectation devenue indisponible ; ne jamais la retirer automatiquement pour contourner.

Chargements validés/génération/locale stable, garde de sortie/unload, sérialisation synchrone et formulaire gelé pendant requête ou résultat incertain. ACK complets restaurant/id ; création/PUT/assignments/delete/duplicate incertains passent par GET seul. Sauvegarde conforme reconnue ; version divergente examinable en détail et adoption confirmée, brouillon conservé. Copie reconnue seulement si nouvelle identité unique, suffixe backend, paramètres équivalents et affectations vides. Sinon liste actualisée à revoir sans POST implicite.

Limites : backend sans ETag/idempotence, identification d’une copie concurrente identique ne peut être prouvée par un identifiant de requête. Auto-nouvelles catégories peut rendre un retour différent du payload ; version serveur présentée sans inventer de succès. Pas de garde SPA globale. Le rendu du lien LearnMore partagé et les libellés génériques de statut restent à revoir dans la finition transversale. Toutes API et impressions simulées, aucune preuve de matériel physique revendiquée. Voir progress/verification pour25 scénarios compilés et validation complète.
