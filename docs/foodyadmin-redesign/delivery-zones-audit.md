# Zones de livraison — audit préalable

Page483 lignes, composant ZoneMap complet, parsePrice partagé avec Tournées et API CRUD/geocode/settings lus. Backend delivery/zones.go CRUD/handlers/ResolveDelivery, zones_eval.go, modèles DeliveryZone et contrat settings MinimumOrderDelivery/route RBAC lus. Comparables : Profils d’impression, Appareils, Codes promotionnels.

La lecture ET toutes mutations de zones exigent orders.manage (pas settings.edit). GET settings exige settings.view/edit et PUT exige settings.edit. La page actuelle utilise settings.edit pour toutes actions, puis charge indistinctement les deux contrats ; garde générique settings empêche un gestionnaire de commandes seul d’y accéder. À corriger dans route/navigation et chargements indépendants, sans modifier le backend. RestaurantID vient du contexte JWT/EnforceRestaurantAccess, query et header restent cohérents.

ZoneInput remplace nom/type/géométrie/villes/frais/minimum, bool is_active et tour_only sont des pointeurs préservés si omis. Tour-only exclu du parcours livraison classique et de cette page ; ne jamais envoyer ces objets par accident. Delete soft-delete protège toute tournée vivante liée avec409. Zone fee null/absent = gratuit ; minimum null/absent = global, zéro distinct. Sans aucune zone active non-tour, ResolveDelivery retourne livrable partout ; cela ne remplace pas les autres conditions de commande. MatchZone prend le premier match du slice serveur, pas le tarif le moins cher ; ne pas trier les données serveur pour redéfinir cette priorité. Lecture ListZones ordonnée created_at, ResolveDelivery n’impose pas d’ordre SQL explicite : limite backend à signaler, pas de nouvelle priorité UI.

Les handlers ne valident que nom/type required ; pas de validation géométrique/prix exhaustive et pas d’unicité nom ou clé d’idempotence. Créer après réponse perdue doit comparer les nouvelles identités et le payload, ne pas répéter automatiquement un POST. UPDATE/DELETE peuvent être vérifiés par GET. Aucun ETag ; concurrence non résolue par un thème. Minimum global est un PATCH logique via PUT settings, n’envoyer que minimum_order_delivery ; conserver zéro et ne pas transformer un champ vide en0 implicitement.

Défauts existants : chargement zones sans catch et settings avec catch vide, formulaire/suppression sans garde/confirmation/verrou, édition possible dans le formulaire pour un rôle sans droit (API bloque), erreurs brutes, booléens et boutons sans label, alignements physiques et couleurs claires locales. Rayon : toPayload prend restaurantCenter au lieu du centre enregistré et peut déplacer silencieusement une zone lors d’un simple changement de tarif ; préserver le centre existant et rendre tout remplacement explicite. Géocodage indisponible distinguable de found=false via API, actuellement fusionné. Polygon legacy doit rester visible/conservé, sans inventer un nouvel outil de dessin. Villes/code postal saisis et géométrie cachée conservés dans le brouillon.

ZoneMap : MapContainer ne réagit pas automatiquement au nouveau center, marker vert est actuellement affiché même pour le cadrage par défaut Tel-Aviv, rayon invalide pourrait atteindre Leaflet. Prévoir recentrage contrôlé, différencier cadrage et position connue, ne dessiner que des géométries valides sans effacer les données enregistrées ; aucune capture ne doit faire passer un fond de carte synthétique pour une vraie couverture. Tiles/geocoding et API seront interceptés, aucune donnée métier ni adresse client réelle.

Aucune source de ce lot n’a encore été modifiée. Profils d’impression est en validation compilée avant la prochaine implémentation.

## Implémentation et preuves

Lot réalisé et documenté : page, minimum indépendant, ZoneMap et helpers de validation/sérialisation, navigation/permissions. 27 scénarios dev puis compilés dans la passe74 avec matériel/imprimantes. États de carte chargés avant capture. Les données synthétiques indiquent « Carte simulée ». Voir verification.md pour résultats exacts.

Limites conservées : aucune transaction/clé d’idempotence/ETag ajoutée au backend ; une création concurrente identique reste ambiguë, une vérification divergente garde le brouillon et montre les données sauvegardées. Garde de fermeture/rechargement locale, pas encore de garde SPA globale. Le polygone historique est visible et conservé ; l’interface n’invente pas d’outil de dessin absent. Contraste/densité et matrices plus larges seront repris lors de la finition transversale.
