## Sections

API admin list/create/update/deleteSections + SectionInput, serveur internal/floorplan/service.go 34–198 et handler.go 30–105 lus. Routes protégées EnforceRestaurantAccess et mutations TablesManage. GET renvoie sections restaurant avec Tables non nulles, tri sort_order/created_at ; filtre ensuite selon tableassignments.ResolveScope. Un compte peut donc n’en voir qu’une partie (tables.manage ne constitue pas à lui seul un bypass, contrairement à owner/staff.manage). Ne pas présenter le nombre visible comme un inventaire exhaustif des suppressions.

Création : nom trim, doublon insensible à la casse refusé ; section puis tables créées **sans transaction**. Label sert de préfixe (UI existante name=label), count0 laisse section vide, sinon noms « label 1 », « label 2 », etc., QR codes serveur aléatoires, active=false. CustomNames existe API mais pas offert par cette page héritée ; ne pas en inventer un besoin. Bornes client 0..50, serveur pas de bornes. Une erreur peut laisser la section et seulement quelques tables : ne pas répéter automatiquement le POST. Relecture et signalement des données présentes nécessaires après échec ; pas de promesse d’idempotence sur réponse perdue. Une section trouvée avec même nom ne prouve pas que notre requête l’a créée (concurrence possible).

Renommage : trim, doublon insensible à la casse, scope restaurant ; réponse ne précharge pas Tables. Conserver le tableau local ou recharger, ne pas afficher zéro sur cette seule réponse. Suppression : soft-delete section + tables, efface placements dans tous les plans. **Sans transaction, erreurs intermédiaires Pluck/Delete ignorées par le service** ; pas de garde contre commandes actives dans cette méthode. Ces défauts serveur préexistants sont à documenter séparément, pas à masquer par une prétendue suppression atomique de tous les objets. Ne pas déduire occupation du simple flag active.

Ancienne UI : prompt/confirm/alert natifs, GET sans catch/retry, création sans verrou instantané, fermeture possible via overlay pendant write, reload échoué peut entraîner répétition. Prévoir vrais dialogues nommés, focus/RTL, scope/réponses périmées, confirmation cascade explicite, reçus avant GET, reprise de GET seulement après ACK, état partiel après erreur ambiguë, permissions et cardinalités lisibles. Les noms longs sont aujourd’hui tronqués ; grille responsive à reprendre.
